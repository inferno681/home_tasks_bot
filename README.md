# home-tasks-bot

Telegram-бот для трекинга домашних дел: текст/фото/текст+фото, дедлайны, напоминания, отметка "сделано".

## Установка

1. Создать бота через @BotFather, получить токен.
2. `uv sync` — поставит зависимости и создаст `.venv`.
3. Скопировать `.env.example` в `.env` и заполнить `BOT_TOKEN` и `MONGO_URI` (строка подключения из Atlas). Секреты читаются напрямую из переменных окружения (`pydantic-settings`, без `python-dotenv` в коде) — `.env` используется только как файл для `uv run --env-file .env`.
4. `uv run --env-file .env python main.py`

## Polling vs webhook

Режим переключается `service.webhook` в `config/config.yaml`:
- `webhook: false` (по умолчанию) — long polling, ничего дополнительно не нужно.
- `webhook: true` — поднимается aiohttp-сервер (`service.web_server_host/port`), бот регистрирует вебхук на `service.base_webhook_url + service.webhook_path` и проверяет каждый запрос по `WEBHOOK_SECRET` из `.env`. `base_webhook_url` должен быть реальным HTTPS-адресом, за который Telegram сможет достучаться (домен + реверс-прокси/туннель) — локально работает только polling. `WEBHOOK_SECRET` и `base_webhook_url` обязательны при `webhook: true` — без них конфиг не соберётся (валидация при старте).

## Как это работает

- `/new` — бот спрашивает текст/фото → (пул, если включено в `/settings`) → категорию → срок (или "нет") → повтор (если срок задан). Задача сохраняется в коллекции `tasks`.
- `/list [категория]` — показывает все задачи со `status: pending` (опционально отфильтрованные по категории), с кнопками "Готово", "Изменить" и "Удалить".
- `/history` — выполненные задачи (`status: done`), по `HISTORY_PAGE_SIZE` (5) штук на странице, от последней выполненной к первой (`Task.completed_at`, проставляется при переходе в `done` — и разовой отметкой "Готово", и кнопкой "Завершить повтор"). Одно сообщение на страницу, с кнопками "◀️"/"▶️" (`bot/handlers/history.py:cb_history_page`), которые правят то же сообщение, а не шлют новое. Кнопок навигации нет, если страница единственная.
- Раз в минуту `scheduler.py` ищет задачи с истёкшим `due_at` и `reminded: false`, шлёт напоминание и помечает `reminded: true`.

## Категории

Топ-3 самые используемые категории (агрегация по `Task.category` в `bot/categories.py`, без отдельной коллекции) показываются кнопками при создании задачи; можно вписать свою — она пополнит общий список для всех в доме. `/list <категория>` фильтрует по ней.

## Назначение

`/assign <id задачи из /list> <@username>` (только владелец) — предлагает второй стороне стать
ответственным за задачу. Как и `/share`, требует подтверждения: адресату приходит запрос с
кнопками "Принять"/"Отклонить"; согласие одним атомарным апдейтом ставит `Task.assigned_to` и
добавляет в `shared_with` (`bot/handlers/list_tasks.py:cb_assign_accept`).

## Пулы задач

Именованные группы пользователей с общим списком задач — отдельная сущность `Pool` (`name`,
`members`), а не бинарное "объединение" двух аккаунтов: один и тот же пользователь может состоять
сразу в нескольких пулах (например "Семья" и "Дача").

`name` ничем не защищено от повторов — ни глобально, ни у одного пользователя (`/newpool` не
проверяет существующие). Пока пулы не пересекаются по составу, это не проблема: `/invite`/`/leave`/
`/kick` всегда ищут пул через `Pool.members == uid`, то есть только среди ваших. Проблема
появляется, если вы сами оказываетесь в двух РАЗНЫХ пулах с одинаковым именем (пригласили в два
разных "Дача", или создали два своих с одним названием) — тогда команда по одному имени не может
понять, какой из них вы имеете в виду. Поэтому у каждого пула есть короткий id (`Pool.short_id` —
последние 6 hex-символов ObjectId), который показывают `/pools` и кнопки-пикеры (`bot/keyboards.py:
task_pool_choice_kb`/`settings_kb`) в формате "Название #a3f9c1". Если по голому имени находится
больше одного вашего пула, `/invite`/`/leave`/`/kick` не гадают, а просят уточнить и перечисляют
кандидатов; уточнение — тот же текст с `#id` в конце (`bot/handlers/pools.py:_resolve_pool`).

- `/newpool <название>` — создать пул, создатель сразу становится единственным участником.
- `/invite <название пула> <@username>` — позвать в пул, в котором вы уже состоите (пул ищется
  по имени среди ваших). Второй стороне приходит запрос с кнопками "Принять"/"Отклонить" —
  в отличие от `/share` (расшаривает одну конкретную задачу без подтверждения), вступление в пул
  открывает доступ ко всем его задачам, своим и будущим, поэтому требует явного согласия.
- `/pools` — список пулов, в которых вы состоите, с числом участников.
- `/leave <название пула>` — выйти из пула; если вы были последним участником, пул удаляется
  целиком (осиротевших пустых пулов не остаётся).
- `/kick <название пула> <@username>` — только создатель пула (`Pool.created_by`) может исключить
  участника; исключённому приходит уведомление.
- Задача попадает в пул через `Task.pool_id`; `None` = личная (видна только автору + `shared_with`
  по `/share`). `/list`, отметка "Готово"/удаление и напоминания (`bot/scheduler.py:
  _reminder_recipients`) учитывают членство в пуле — все участники видят задачи друг друга,
  могут их закрывать и получают общие напоминания.
- Защиты от повторной отправки одного и того же приглашения пока нет.

## Настройки создания задач

`/settings` — куда попадают новые задачи из `/new`, инлайн-кнопками:

- Пул по умолчанию (`User.default_pool_id`, `None` = личные) — молча подставляется при создании,
  без лишнего шага в `/new`.
- "Спрашивать пул при создании" (`User.ask_pool_on_create`) — если включено и у вас есть хотя бы
  один пул, `/new` после текста/фото добавляет шаг выбора пула вместо тихой подстановки дефолта.

## Повторяющиеся задачи

При создании задачи со сроком можно включить повтор — "через N дней" или "по дням недели" (`bot/recurrence.py:next_due_date`, чистая функция, покрыта тестами в `tests/test_recurrence.py`). При нажатии "Готово" на повторяющейся задаче она не помечается `done`: `due_at` сдвигается на следующую дату, `reminded` сбрасывается, а момент выполнения добавляется в `Task.completed_history` — тот же документ, а не новый, история хранится прямо в нём.

На карточке такой задачи есть отдельная кнопка "⏹ Завершить повтор" (`bot/handlers/list_tasks.py:cb_finish_recurring`) — она переводит задачу в `status: done` напрямую, минуя пересчёт `due_at`, когда повтор больше не нужен (единственная альтернатива раньше — полное удаление задачи). Доступна тому же кругу, что и "Готово"/"Удалить".

## Редактирование задачи

Кнопка "✏️ Изменить" на карточке из `/list` (доступна тому же кругу, что и "Готово"/"Удалить" —
владельцу, `shared_with`, участникам пула задачи, `bot/task_access.py:is_task_authorized`)
открывает меню полей: текст/фото, категория, срок, повтор, пул. Каждое поле редактируется тем же
UI, что и при создании через `/new` (переиспользует `category_choice_kb`/`deadline_choice_kb`/
`repeat_choice_kb`/`task_pool_choice_kb`), но применяется сразу и независимо — правка одного поля
не спрашивает остальные, в отличие от последовательного мастера `/new`.

- id редактируемой задачи хранится в `FSMContext`-данных (`edit_task_id`), а не в `callback_data`
  каждого шага — в отличие от `requester_id` в диплинках, это не то, что пользователь может ввести
  сам, так что здесь это не проблема безопасности; авторизация всё равно перепроверяется на каждом
  финальном шаге на случай, если доступ к задаче отозвали посреди редактирования.
- "Повтор" недоступен, пока у задачи нет срока (совпадает с логикой `/new`, где повтор вообще не
  спрашивается без срока) — попытка открыть его без срока отвечает алертом, а не молча ломает
  задачу несогласованным состоянием.
- Снятие срока (кнопка "Без срока" или текст "нет") заодно сбрасывает `repeat_every_days`/
  `repeat_weekdays` — иначе они остались бы висеть без даты, от которой считать следующее
  повторение.

## Docker / CI/CD

- `docker build -t home-tasks-bot .` — образ на `python:3.12-slim`, зависимости через `uv sync
  --no-dev` прямо в системный python (`UV_PROJECT_ENVIRONMENT=/usr/local`), рантайму нужны только
  `main.py`, `bot/`, `config/`.
- `.github/workflows/main.yml`: `test` (pytest + coverage → Codecov) и `lint` (flake8/wemake +
  isort + mypy) идут параллельно → `build_and_push_to_docker_hub` → `deploy` (SCP
  `infra/docker-compose-prod.yaml` на сервер, `docker compose pull/down/up` по SSH) → `send_message`
  (уведомление в Telegram). Пайплайн срабатывает на push в `main`.
- Нужные секреты репозитория: `DOCKERHUB_USERNAME`, `DOCKERHUB_PASSWORD`, `CONTAINER_NAME`,
  `CODECOV_TOKEN`, `HOST`, `USER`, `SSH_KEY`, `SSH_PASSPHRASE`, `PROJECT_NAME`, `TELEGRAM_TO`,
  `TELEGRAM_TOKEN` — заводятся в настройках репозитория на GitHub, в коде их нет.
- Локально: `uv run flake8 .`, `uv run isort --check-only .`, `uv run mypy .`, `uv run pytest`.

## Хранилище FSM-состояний

Переключается `fsm.storage` в `config/config.yaml` (`bot/fsm_storage.py:build_fsm_storage`):

- `memory` (по умолчанию) — `MemoryStorage`, ничего дополнительно не нужно; на рестарте бота
  все незавершённые диалоги (`/new` и т.п.) теряются, пользователю нужно начать заново.
- `redis` — `RedisStorage`, переживает рестарт бота. Адрес — `redis.host`/`redis.port`/`redis.db`
  в `config.yaml`, пароль — необязательный `REDIS_PASSWORD` в `.env` (пусто = без авторизации).
  `infra/docker-compose-prod.yaml` не поднимает Redis сам — при деплое с `fsm.storage: redis`
  нужен отдельный Redis, доступный контейнеру по этому адресу (`localhost` внутри контейнера —
  это сам контейнер, не хост). При недоступном Redis бот падает сразу при старте (явный `ping`
  в `main.py`), а не молча на первом `/start` пользователя.
- `mongo` — `PyMongoStorage` (не путать с deprecated `MongoStorage` на motor), переиспользует уже
  открытое соединение к Atlas из `bot/db.py` — не плодит второй клиент. Коллекция —
  `fsm.mongo_collection` (по умолчанию `fsm_states`) в той же базе, что и `tasks`/`users`.

При `redis`/`mongo` FSM-состояние переживает деплой/рестарт контейнера; при `memory` — нет.

## О выборе БД-слоя

Изначально использовался `motor`, но MongoDB задепрекейтила его 14.05.2025 в пользу нативного async-API прямо в `pymongo` (`AsyncMongoClient`) — этот EOL уже наступил (14.05.2026). Поэтому проект использует `beanie` — ODM поверх `pymongo`'s `AsyncMongoClient`, даёт Pydantic-модели вместо сырых словарей (`Task.find(...)`, `task.save()`, `task.delete()` вместо ручных `insert_one`/`update_one`).

## Часовой пояс

При первом `/start` (а если его пропустили — при первом `/new` или `/list`) бот просит смещение от UTC (`+3`, `-5`, `+5:30`) и хранит его в коллекции `users` (`utc_offset_minutes`); без этого `/new`/`/list` не пускают дальше (`bot/handlers/common.py:ensure_timezone`). Ввод дедлайна конвертируется в UTC этим смещением, вывод — обратно в локальное время. Смещение фиксированное (без DST) — см. `ponytail:`-комментарий в `bot/handlers/common.py`.

## Шеринг задач

- `/share <id задачи из /list> <@username>` — предложить расшарить свою задачу (только владелец).
  `/list` показывает `id` каждой задачи текстом. Как и `/invite`/`/assign`, требует подтверждения
  второй стороны — расшаривание одной задачи не такое серьёзное решение, как `/merge` был бы, но
  всё равно даёт постороннему доступ к чужой задаче, поэтому без явного "да" не делается.
- Коллекция `users` (`user_id`, `username`, `utc_offset_minutes`) пополняется middleware'ом (`bot/middlewares.py`) на каждом апдейте, чтобы `username → user_id` был свежим.
- `/list`, `done`, `delete` видят личную задачу (`pool_id is None`) только автору, задачу из пула — всем его участникам, плюс `shared_with` поверх обоих случаев (`bot/handlers/list_tasks.py:_open_tasks_for`/`_authorized`); равенство скаляра с полем-массивом — стандартная семантика Mongo для проверки вхождения. Добавление в `shared_with` — атомарный `AddToSet`, чтобы параллельные подтверждения не затирали друг друга.

## Приглашения по ссылке (диплинки)

`/share`, `/assign` и `/invite` рассчитаны на то, что адресат уже писал боту хоть раз (иначе бот
не может отправить ему сообщение). Если это не так, вместо ошибки в тупик пользователь получает
ссылку вида `https://t.me/<bot>?start=<payload>` (`bot/deeplinks.py:build_start_link`). `payload`
кодирует само предложение (`{share|assign|pool}_{id}_{requester_id}`, только `[A-Za-z0-9_-]` — так
Telegram ограничивает `/start`-параметр, поэтому подчёркивания, а не двоеточия как в обычном
`callback_data`). Как только адресат переходит по ссылке и нажимает "Start":

- если у него ещё не задан часовой пояс — сначала как обычно спрашивается смещение от UTC, а
  предложение остаётся в `FSMContext`-данных (`pending_payload`) до его ответа;
- как только пояс известен, бот показывает ровно ту же карточку с кнопками "Принять"/"Отклонить",
  что получил бы уже зарегистрированный пользователь (`bot/deeplinks.py:resolve_pending_action`,
  `bot/handlers/common.py:cmd_start`/`set_timezone`).

Если задача/пул к этому моменту уже удалены — ссылка просто ничего не показывает, без ошибки.
